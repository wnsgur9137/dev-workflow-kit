## 산출물
위치: `~/.local/share/dev-workflow-kit/security/reports/<run-id>/` (플러그인 폴더 밖 → [[ADR-006 플러그인 마켓플레이스 구조]])
```text
<run-id>/
├── raw/                 # 도구 원본 출력·실행 기록 (Claude 기본 열람 대상 아님)
│   ├── semgrep.json       # scan-code
│   ├── gitleaks-git.json  # scan-code, git 히스토리 (git 저장소일 때만)
│   ├── gitleaks-dir.json  # scan-code, 작업 트리
│   ├── osv.json           # scan-code
│   ├── checks.json        # scan-code, 스택 검사 (scripts/lib/checks.py)
│   ├── *.log              # 도구별 로그
│   ├── status.tsv         # 도구별 실행 결과 <도구>\t<ok|failed|skipped>\t<종료코드>\t<메모>
│   ├── profiles.tsv       # 감지된 프로파일과 하위 경로
│   ├── plan.tsv           # Semgrep 규칙셋·제외 경로 조립 결과
│   ├── warnings.txt       # 스캔 스크립트가 남긴 경고
│   ├── meta-in.json       # normalize.py 에 넘기는 메타
│   ├── mobsf.json         # scan-app — MobSF 리포트 정제본 (secrets·strings 등은 개수만, 원본 mobsf-full.json 은 정규화 후 삭제)
│   ├── gitleaks-artifact.json  # scan-app — 산출물(ZIP) 내부 Gitleaks
│   └── zap.json           # scan-web (예정)
├── findings.json        # 정규화된 전체 결과
├── summary.md           # Claude가 읽는 요약
└── meta.json            # 도구 버전, 이미지 digest, 대상, 시간
```

## 정규화 규칙
- **severity 통일**: `critical / high / medium / low / info`. 도구별 매핑표는 각 도구 노트에 둔다.
- **evidence 제한**: 최대 200자, 제어문자 제거, 시크릿 패턴 재마스킹. → [[시크릿 처리]]
- **신뢰하지 않는 텍스트 표시**: `summary.md`에서 도구가 추출한 문자열(APK 문자열, HTTP 응답 등)은 코드 블록 안에 넣고 "데이터"임을 명시한다. → [[위협 모델#T5 프롬프트 인젝션]]
  - 자유 텍스트 — 설명(Semgrep 메시지는 대상 코드가 메타변수로 치환된 값, OSV 요약에는 패키지 이름), 조치, 근거, 경고, 도구 오류 내용 — 는 ` ````text ` 코드 블록 안에만 둔다. 표에는 넣지 않는다.
  - 짧은 식별자 — 위치(경로·패키지), 규칙 ID, 프로파일 라벨, 참고 ID — 는 인라인 코드로 감싼다. 백틱·파이프는 치환하고 200자로 자른다.
  - 데이터 안의 백틱 3개 이상은 깨뜨려 코드 블록을 닫지 못하게 한다.
- **중복 제거**: `id` 기준.
- **베이스라인**: 같은 종류·같은 대상(`--target` 값)의 **직전 실행**과 `id` 로 비교해 신규·유지·해결을 표시한다 (P4, `scripts/lib/baseline.py`). 거짓 "해결"·"신규"를 줄이는 규칙은 아래와 같다 (PR #40 리뷰)
  - **비교 단위**는 `status.tsv` 의 도구(`unit`)다. 두 실행 모두에서 **완전했던 단위**만 비교한다. 완전하다는 것은 status 가 `ok` 이고, 결과 파일을 읽어 해석했고, 부분 오류가 없다는 뜻이다. 부분 오류는 semgrep 의 파일별 오류, checks 의 시간 초과·검사 실패·결과 상한, 파서가 돌려준 오류다. 완전한 단위는 `meta.json` 의 `complete_units` 에 남는다. 어느 쪽이든 실패·건너뜀·부분 결과면 그 도구 결과는 `not-compared` 다
  - **비교 키**(`meta.json` 의 `unit_keys`)는 id 계산 버전, 플러그인 버전, 도구 이미지 digest, (semgrep) 규칙 커밋, (semgrep·checks) 프로파일 목록의 해시다. 키가 다르면 그 단위는 비교하지 않는다(`changed_units`). 규칙·도구·파서가 바뀌면 코드와 무관하게 결과가 생기거나 사라지기 때문이다. 그래서 플러그인을 올린 직후 첫 실행은 비교하지 않는다. OSV DB 날짜는 키에 넣지 않는다 — DB 갱신으로 새 취약점이 "신규"로 보이는 것은 의도한 동작이다. 제외 경로 설정은 키에 없다(프로파일이 같으면 같다고 본다)
  - **위치 이동**: `id` 에 줄 번호가 들어 있어 위쪽에 줄이 추가되면 같은 결과의 id 가 바뀐다. 정확히 같은 id 를 맞춘 뒤 남은 신규·해결을 (단위, 규칙, 파일·URL, 패키지)별로 개수만큼 짝지어 `moved` 로 센다. 같은 파일에서 규칙이 같은 결과가 하나 고쳐지고 다른 곳에 하나 생기면 이것도 이동으로 보인다(보수적으로 "유지"에 가깝게 센다)
  - **해결** = 직전 실행에 있었고 이번에 없는(이동으로 짝지어지지 않은) 결과다. 처음 50건을 `meta.json` 의 `baseline.resolved_items` 와 summary 표에 남긴다. "고쳤다"가 아니라 "이번에 보이지 않음"이다. 웹(zap)은 크롤링 범위에 따라 달라질 수 있다고 summary 에 함께 적는다
  - 기준은 **직전 실행 하나**다. 단위별로 "가장 최근 완전 실행"을 찾지 않으므로, 한 번 실패한 도구는 다음 실행에서도 비교하지 않는다(보수적 선택)
  - 직전 실행이 없거나(보관 기간 30일이 지나 지워진 경우 포함) 이전 버전 리포트(`complete_units`·`unit_keys` 없음)이면 비교하지 않고 이유를 적는다. 링크로 된 실행 폴더·`meta.json`, 이름이 이번 실행보다 나중인 실행은 고르지 않는다. 같은 초의 접미사(`-2`~`-1000`)는 숫자로 정렬한다
  - web 의 대상 키는 질의 값을 가린 URL 이다 — 질의 값만 다른 URL 은 같은 대상으로 본다(ZAP 결과는 출처 단위라 영향이 작다)
  - 이전 실행의 `findings.json` 도 도구가 대상에서 뽑은 데이터다. 링크·64MB 넘는 파일은 읽지 않고, 심각도는 정해진 값만, 도구·위치·규칙은 짧은 식별자로 잘라 인라인 코드로만 보인다

## summary.md 구성
1. 메타: 대상, 시간, 프로파일, 도구 버전
2. 심각도별 개수
3. 이전 실행과 비교 — 기준 run-id, 신규·유지(위치 이동)·해결 개수, 해석 주의, 비교하지 않은 도구(바뀜·실패), 해결된 결과 표. Critical/High 제목과 Medium 이하 표의 심각도 옆에 `[신규]`
4. Critical/High 목록 — 제목(심각도·도구·규칙), 위치·프로파일·분류, 참고, id, 그리고 설명·조치·근거를 담은 코드 블록 하나
5. Medium 이하는 개수 + 상위 N개 표(번호·심각도·도구·위치·규칙)와, 같은 번호로 설명을 담은 코드 블록
6. 경고 — 코드 블록 안에 목록으로
7. 실행 중 오류·건너뛴 도구 — 표(도구·상태·종료코드)와 내용을 담은 코드 블록 (누락 은폐 금지)
