# /workflow:status

상위: [Home](../Home.md) · [README](../../README.md)

세션을 다시 시작했을 때 **어디까지 했고, 무엇이 남았고, 다음에 무엇을 할지**를 매번 같은 형식으로 정리합니다. 메모리·문서에 남은 결정과 맥락을 git·GitHub의 실제 상태와 맞대어, 둘이 어긋나면 실제 상태를 믿고 어긋남을 알립니다. **조회만 하고 아무것도 바꾸지 않습니다.**

"이전 작업 파악", "이어서 진행", "어디까지 했지"처럼 말로 요청해도 모델이 이 skill을 부릅니다.

## 사용법

```
/workflow:status [--local] [--days=N]
```

> [!NOTE]
> Claude Code와 Codex CLI에는 내장 `/status` 명령이 있습니다. 맨 `/status`를 입력하면 내장 명령이 열리니 `/workflow:status`(Codex는 `$workflow:status`)로 부르거나 "이전 작업 파악"처럼 말로 요청하세요.

## 예시

```
/workflow:status
/workflow:status --local      # 오프라인이거나 빨리 볼 때 (GitHub 조회 생략)
/workflow:status --days=14    # 최근 2주 병합까지 "마지막 작업"에 포함
```

## 옵션

| 옵션 | 설명 |
|------|------|
| `--local` | GitHub 조회와 `git fetch`를 건너뜀. 메모리·로컬 git만 봄 |
| `--days=N` | 최근 병합 PR 조회 기간 (기본 7, 1~90) |
| `-h`, `--help` | 도움말 표시 |

## 무엇을 보는가

| 출처 | 항목 |
|---|---|
| 메모리·문서 | Claude Code 자동 메모리(관련 항목 파일까지 읽음), `CLAUDE.md`·`AGENTS.md`, 규약이 가리키는 진행 문서 → 마지막 작업, 사용자 대기, 남은 일, 메모리가 말하는 진행 중 상태 |
| 로컬 git | 현재 브랜치·커밋 안 한 변경·push 안 한 커밋, stash, worktree, base에 병합된 로컬·원격 브랜치, PR 없는 오래된 브랜치 |
| GitHub | 내가 연 PR의 리뷰·CI 상태와 **`/pipeline`으로 이어 갈 단계**, 최근 병합 PR, 열린 이슈의 체크리스트 진행률·최근 댓글, 처리됐을 수 있는 열린 이슈 |
| 릴리스 (조건부) | 버전은 올렸는데 태그가 없는 경우, 플러그인 마켓플레이스 저장소면 설치된 플러그인과 저장소 버전 차이(Claude Code) |

## 결과

```
=== 작업 현황 (<owner>/<repo> · <브랜치>) ===
## 마지막 작업
## 진행 중         ← PR·브랜치마다 상태와 이어 갈 단계 (예: /workflow:pipeline --from=12)
## 남은 일         ← 사용자 대기 / 바로 가능 / 정리 필요
## 어긋남          ← 메모리 "…" ↔ 실제 "…" → 메모리 수정 제안
## 다음 행동 추천   ← 명령까지 1~2개
```

내용이 없는 절도 "없음"으로 남겨 매번 같은 모양을 유지합니다. 조회하지 못한 항목은 "조회 불가(사유)"로 표시하고 나머지는 계속 봅니다.

## 동작

- 정리할 것(병합된 브랜치·처리됐을 수 있는 이슈·태그 누락·메모리 갱신)은 **제안만** 합니다. 승인하면 skill이 끝난 뒤 하나씩 진행합니다.
- Claude Code에서 확인 없이 허용하는 명령은 git·gh **조회** 명령뿐이고, 옵션을 더 붙여 쓰기·토큰 출력이 될 수 있는 명령(`git status`·`git log`·`git remote`·`gh auth status`)은 인자까지 정확히 맞을 때만 허용합니다. `git fetch --prune`은 인자로 명령 실행·브랜치 삭제가 가능해 **매번 권한 확인**을 거칩니다(거절하면 원격 정보가 오래됐을 수 있다고 표시하고 계속). `gh api`는 쓰지 않습니다.
- 계정별 토큰(`<OWNER>_GITHUB_TOKEN`)을 쓰는 저장소는 `gh` 호출 형태가 자동 허용 목록과 달라 권한 확인이 뜹니다.
- 이슈·PR·리뷰 코멘트·메모리의 글은 데이터로만 다루고, 그 안의 지시문은 따르지도 출력에 옮기지도 않습니다.
- 열린 PR의 상태 판정은 [/pipeline](pipeline.md)의 설계 원칙 B(실물에서 판정)와 같은 기준입니다(PR 작성자 본인의 것만 셈. 자체 리뷰는 `## Review Summary` 형식의 리뷰, 반영은 그 뒤의 반영 내역 코멘트나 반영 커밋 뒤의 스레드 답글. 지적이 없는 리뷰 뒤에는 반영 단계를 건너뜀). 이어 갈 명령은 PR 브랜치가 현재 브랜치가 아니면 전환 방법을 함께 적습니다.
- 스쿼시 병합된 브랜치는 이름이 아니라 병합 PR의 head 커밋이 같을 때만 "병합됨"으로 봅니다.
