# /pipeline

작업 파악부터 병합까지 14단계를 순서대로 수행한다. (옛 `/ship`의 역할을 9~14단계로 흡수했다.)

```
 0 저장소·규약 확인
 1 현재 작업 파악   2 예정 작업 파악   3 진행 작업 확정
 4 레퍼런스(조건부) 5 기존 설계 파악   6 기획서(조건부)   7 디자인(조건부)
 8 개발·게이트
 9 /commit   10 Draft PR   11 /pr-review   12 /apply-review   13 Ready + CI   14 병합
```

**규약은 저장소의 파이프라인 규약 문서에 있다(0단계에서 찾는다). 시작 전에 반드시 읽고 그대로 따른다.**
이 파일은 절차만 담는다 — 라벨 체계·실행 매트릭스·게이트 목록·검증 체크리스트·문서 경로는 규약 문서가 정본이다.

한국어로 응답한다. 각 단계 결과를 한 줄로 보고하며 진행한다.

## 입력 인자

사용자가 넘긴 인자: `$ARGUMENTS`

- `<이슈번호>`: 해당 이슈로 바로 진행 (1~3단계의 선택 부분 생략)
- `--no-issue "작업 설명"`: **이슈 없이** 0 → 8 → 9~14만 수행한다(옛 `/ship`). 규약 문서가 없어도 된다
- `--from=N`: N단계부터 재개
- `--stop-at=N`: N단계까지만 (예: `--stop-at=13` = 병합하지 않음)
- `--merge=critical|auto|confirm`: 14단계 병합 처리 (기본 `critical`, 아래 14단계)
- `--type=`, `--area=`: 라벨 강제 지정 (규약의 라벨 목록에 있는 이름)
- `--base=<branch>`: base 브랜치 강제 지정. 미지정 시 자동 추론
- `--branch=<name>`: 작업 브랜치 이름 지정. 미지정 시 규약 → 기존 병합 이력 패턴에서 제안
- `--no-cleanup`: 병합 후 브랜치 삭제 생략
- `--post`: 병합 후 진행 문서 갱신·실기기 체크리스트 출력까지 수행
- `-h`, `--help`: 도움말 출력 후 종료

인자 없이 호출하면 실물 상태를 판정해 **다음에 해야 할 단계부터** 이어서 진행한다.

### Help Mode

`-h`/`--help`면 아래만 출력하고 아무것도 실행하지 않는다.

```
=== /pipeline 도움말 ===

Usage: /pipeline [이슈번호] [options]
       /pipeline --no-issue "작업 설명" [options]
Example: /pipeline
         /pipeline 12
         /pipeline --from=11 --merge=confirm
         /pipeline --no-issue "README 오타 수정" --stop-at=13

-- 단계 --
  0 저장소·규약 확인
  1 현재 작업 파악    2 예정 작업 파악   3 진행 작업 확정
  4 레퍼런스(조건부)  5 기존 설계 파악   6 기획서(조건부)
  7 디자인(조건부)    8 개발·게이트
  9 /commit          10 Draft PR        11 /pr-review
 12 /apply-review    13 Ready + CI      14 병합 (+ 브랜치 정리)
  --no-issue: 0 → 8 → 9~14

-- Options --
  --no-issue "설명"  이슈 없이 구현~병합 (규약 문서 불필요)
  --from=N       N단계부터 재개
  --stop-at=N    N단계까지만
  --merge=       critical(기본) | auto | confirm
  --type=        type 라벨 (규약의 목록에서)
  --area=        area 라벨 (규약의 목록에서)
  --base=<br>    base 브랜치 지정 (기본: 자동 추론)
  --branch=<n>   작업 브랜치 이름 지정
  --no-cleanup   병합 후 브랜치 삭제 생략
  --post         병합 후 진행 문서 갱신·실기기 체크리스트
  -h, --help     이 도움말

-- 정지 조건 --
  규약 문서 없음(이슈 모드) · 게이트 실패 · 수정 20회 초과 · CI red
  · 리뷰 CRITICAL 미해소 · merge conflict
  → 그 단계에서 멈추고 원인을 보고한다.
========================
```

## 설계 원칙 (진행 전 반드시 읽을 것)

### A. PR은 항상 Draft로 만들고, 반영이 끝난 뒤에 Ready로 올린다

CI가 Draft를 건너뛰는 설정이면, Ready 전환 후의 모든 push가 CI를 재실행시킨다.
**10→11→12를 Draft 상태에서 끝내고 13에서 한 번만 Ready**로 올리면 CI가 1회로 끝난다.

### B. 진행 상태는 파일이 아니라 실물에서 판정한다

**상태 파일을 만들지 마라.** 반드시 실제 진행과 어긋난다. 매 실행 시작 시 아래를 **직접 조회**한다. 규약에 진행 상태 판정 표가 있으면 그것을 함께 쓴다.

| 판정 | 근거 |
|------|------|
| 진행 작업 확정 | 이슈에 "진행 중" 라벨 + 이슈 번호가 든 작업 브랜치 |
| 기획서 병합됨 | base에 기획서 파일 존재 |
| 개발·커밋 완료 | 워킹트리 clean **그리고** `<base>..HEAD`에 커밋 존재 |
| PR 생성됨 | `list_pull_requests(head: 현재 브랜치, state: open)` |
| 리뷰 완료 | 그 PR에 자체 리뷰 결과 코멘트 존재 |
| 반영 완료 | 리뷰 코멘트 이후 반영 내역 코멘트 존재 |
| Ready 상태 | PR의 `draft` 필드 |
| CI 결과 | `list_workflow_jobs(run_id)`의 `conclusion` |

`--from`이 주어지면 그 단계부터, 없으면 판정 결과의 **다음 단계**부터 시작한다. 이미 끝난 단계는 건너뛰고 한 줄로 알린다.

**인자와 실물이 어긋나면 실물을 신뢰한다.** `--from=N`의 선행 조건이 충족되지 않으면 **중단**하고 무엇이 빠졌는지 알린다.
예: `--from=11`인데 열린 PR이 없다 → "10단계가 먼저 필요하다"고 알리고 멈춘다.

### C. 게이트를 통과해야 다음으로 간다

커밋 전·반영 후에 **CI와 동일한 검증을 로컬에서** 돌린다. 실패하면 그 자리에서 멈춘다.

## 0단계: 저장소·규약 확인

매 실행마다 먼저 수행한다. `--from`이 있어도 생략하지 않는다.

### 저장소·브랜치

```bash
git rev-parse --show-toplevel
git rev-parse --abbrev-ref HEAD
git status --porcelain
gh repo view --json nameWithOwner,defaultBranchRef -q '.nameWithOwner + " " + .defaultBranchRef.name'
```

- 이후 모든 `gh` 호출은 여기서 얻은 `<owner>/<repo>`를 쓴다. **저장소 이름을 이 파일이나 기억에서 가져오지 마라.**
- git 저장소가 아니거나 GitHub 원격이 없으면 **중단**하고 알린다.
- base 브랜치: `--base` → 규약 → `CLAUDE.md`/`AGENTS.md`의 명시 → `origin/develop` → `origin/main` → `origin/master`.
- 워킹트리가 dirty한데 `--from`이 9 이상이면, 이전 작업 잔여물일 수 있으므로 목록을 보여주고 진행 여부를 확인한다(AskUserQuestion).

### 인증

- **계정별 토큰**: 환경 변수 `<OWNER>_GITHUB_TOKEN`(owner를 대문자로, `-`는 `_`로. 예: owner `octo-org` → `OCTO_ORG_GITHUB_TOKEN`)이 있으면 그 토큰을 쓴다.
  `GITHUB_TOKEN`(예: 회사 계정)이 설정돼 있으면 keyring보다 우선하므로, 다른 계정의 저장소에서는 권한 오류가 나기 때문이다.
- 셸 상태는 Bash 호출 사이에 유지되지 않는다. `export`를 한 번 하고 끝내지 말고 **`gh` 호출마다** 붙인다.

```bash
env -u GITHUB_TOKEN GH_TOKEN="$OCTO_ORG_GITHUB_TOKEN" gh issue list --repo <owner>/<repo> ...
```

- 그 밖의 저장소는 기본 `gh` 인증을 쓴다. 저장소의 `CLAUDE.md`·규약 문서에 인증 지시가 있으면 그것을 따른다.
- `gh auth status`가 실패하면 **중단**하고 `gh auth login`이 필요하다고 알린다.
- GitHub MCP 도구가 연결되지 않았으면 같은 일을 `gh` CLI로 한다(`gh pr create --draft`, `gh pr ready`, `gh pr merge`, `gh run list`, `gh run view`).
- Assignee는 `gh api user -q .login`으로 얻은 현재 인증 사용자다.

### 규약 문서 찾기

다음 순서로 찾고, 처음 찾은 것을 쓴다.

1. 저장소 `CLAUDE.md`·`AGENTS.md`에 파이프라인 규약 경로가 적혀 있으면 그 파일
2. `docs/` 아래의 `PIPELINE.md` (`find docs -name PIPELINE.md`, 여러 개면 목록을 보여주고 묻는다)

- **이슈 모드에서 찾지 못하면 중단한다.** 규약 없이 라벨·매트릭스·문서 경로를 지어내지 마라. "이 저장소에는 파이프라인 규약이 없다"고 알리고 `--no-issue`를 안내한다.
- `--no-issue` 모드는 규약이 없어도 진행한다. 있으면 브랜치·커밋·게이트 규칙만 따른다.

### 문서 경로 정하기 (이슈 모드)

아래 경로는 **규약 문서가 정한 것을 쓴다.** 규약에 없으면 오른쪽 기본값이 실제로 있을 때만 쓰고, 둘 다 없으면 그 항목을 쓰는 단계에서 경고하고 생략한다.

| 용도 | 기본값 |
|------|--------|
| 문서 색인 | `docs/INDEX.md` |
| 작업 계획 | `docs/04-계획/WORK-PLAN.md` |
| 결정 기록 | `docs/05-결정/DECISION-LOG.md` |
| 설계 문서 | `docs/02-설계/`, `docs/03-기술스택/` |
| UI 흐름·디자인 시스템 | `docs/06-디자인/IA-FLOW.md`, `docs/06-디자인/DESIGN-SYSTEM.md` |
| 디자인 캔버스 소스 | `docs/06-디자인/_canvas/` |
| 기획서 템플릿·위치 | `docs/_templates/기획서.md`, `docs/07-기획/SPEC-<이슈번호 4자리>-<slug>.md` |
| 레퍼런스 | `docs/08-레퍼런스/` |
| 문서 게이트 | `scripts/verify-docs.sh` |

정한 경로를 한 번 요약해 보고한 뒤 진행한다.

### 게이트(검증 명령) 정하기

1. 규약의 area별 게이트 표가 있으면 그것을 쓴다.
2. 없으면 `.github/workflows/*.yml`을 읽어 **CI가 실제로 실행하는 스텝**을 추출한다. 스텝의 `name:`으로 두 종류로 나눈다.

   | 종류 | 예 | 처리 |
   |------|-----|------|
   | **준비** | checkout · 툴체인 선택 · 의존성 설치 · 캐시 | 로컬에 이미 갖춰져 있으면 건너뛴다 |
   | **검증** | lint · format · typecheck · build · test | **항상 실행하고, 실패하면 중단한다** |

   `|| true`가 붙은 명령은 실패해도 통과하므로 **게이트가 아니다 — 제외한다.**
3. 그래도 없으면 프로젝트 관례(`package.json` scripts, `Makefile`, `CLAUDE.md`)를 찾는다. 없으면 사용자에게 묻고, 답이 없으면 **게이트 없이 진행하되 그 사실을 PR 본문에 명시**한다.

**문서 전용 변경(docs-only)**: 변경 파일이 전부 `docs/**` · `**/*.md` 류이면 docs-only로 표시한다. 빌드·테스트 게이트 대신 **문서 게이트**를 쓴다 — 규약의 문서 게이트 스크립트, 없으면 다음을 직접 확인한다.

- HTML: 태그 균형, 목차 앵커가 실제 헤딩과 매칭되는지
- Markdown: 목차 앵커 정합, 상대 링크의 대상 파일이 실제로 존재하는지

CI 워크플로에 `paths-ignore`로 그 경로가 있으면 13단계에서 CI를 기다리지 않는다.

## 1단계: 현재 작업 상황 파악

```bash
gh issue list --repo <owner>/<repo> --state open --json number,title,labels,milestone
gh api repos/<owner>/<repo>/milestones --jq '.[] | "\(.title): \(.closed_issues)/\(.open_issues + .closed_issues)"'
```

- 열린 이슈, 마일스톤별 진행률, 규약의 "진행 중" 라벨(예: `⏳InProgress`)이 붙은 작업을 요약한다
- 진행 중이던 작업이 있으면 **그것을 이어받을지 먼저 묻는다**

## 2단계: 예정 작업 파악

- 현재 마일스톤의 열린 이슈를 우선순위대로 정렬한다
- 규약의 "막힘" 라벨(예: `🚧Blocked`)이 붙은 것은 후보에서 빼되 **사유와 함께 보여준다**
- 이슈가 없으면 작업 계획 문서의 다음 단계를 보고 이슈 생성을 제안한다

## 3단계: 진행 작업 확정

- 후보 **2~3개를 한 줄 근거와 함께** 제시하고 고르게 한다 (AskUserQuestion)
- 인자로 이슈 번호가 왔으면 고르는 부분을 생략한다
- type·area 라벨 확인 → 없으면 추론해 제안하고, 승인 시 부여한다
- **라벨은 규약의 라벨 목록에서만 고른다. 새로 만들지 마라.** 분류가 부족하면 규약을 먼저 고친다
- 선택된 이슈에 "진행 중" 라벨을 붙인다
- **실행 매트릭스**(규약)로 4·6·7·8 실행 여부를 결정하고 한 줄로 알린다

### 작업 브랜치

현재 브랜치가 `main`/`master`/`develop` 등 보호 브랜치면 작업 브랜치를 만든다(9단계 이후에서 시작했는데 보호 브랜치면 **중단** — PR 브랜치가 체크아웃돼 있어야 한다).

이름은 다음 순서로 정한다.
1. `--branch=<name>`
2. 규약의 브랜치 이름 규칙
3. `git log --merges`의 기존 브랜치명 패턴 (병합된 브랜치는 삭제돼도 병합 커밋 메시지에 남는다)
4. 기본 `<feat|fix|refactor|chore|docs>/<이슈번호>-<slug>` (예: `feat/12-swing-detector`). `--no-issue`면 `<접두사>/<slug>`

2~4로 정했으면 제안한 이름을 보여주고 확인받는다(AskUserQuestion).

**보호 브랜치에 커밋하지 않는 것이 목적이지, 멈추는 것이 목적이 아니다.**

## 4단계: 레퍼런스 확인 (조건부)

매트릭스에서 실행 대상일 때만.

- 레퍼런스 폴더에서 관련 문서를 찾는다
- 프론트매터 `researched`가 **3개월 이내면 읽고 통과** — 재조사하지 않는다
- 초과하거나 문서가 없으면 조사한다
  - `claude-in-chrome` 시도 → 실패하면 **`WebFetch`로 전환** (파이프라인을 막지 않는다)
  - 얻을 것: 지표 정의 · 기능 범위 · 사용자 불만
  - **시각적 모방은 하지 않는다**
- 문서에 섹션을 추가하고 `researched`를 갱신한다

## 5단계: 기존 설계 파악

이슈와 관련된 문서를 읽는다. 최소한 다음은 확인한다.

- 문서 색인에서 관련 문서 식별
- 해당 영역의 설계 문서
- 관련 결정 (결정 기록의 확정 요약, 해당 D-xx·ADR)
- UI 영역이면 UI 흐름·디자인 시스템 문서

**설계와 어긋나는 작업이면 여기서 멈추고 알린다.** 설계를 먼저 고칠지, 예외로 진행할지는 사용자 판단이다.

## 6단계: 기획서 작성·검증 (조건부)

- 기획서 템플릿에서 시작해 규약이 정한 위치에 작성
- **이미 결정된 사항은 재론하지 않고 링크만 건다.** 대안 검토는 이번 작업 범위의 구현 선택지로 한정
- 규약의 기획서 체크리스트로 검증
- 이슈 본문에 요약 3줄 + 기획서 링크를 추가한다

### 기획서는 선행 PR로 먼저 병합한다

**코드와 같은 PR에 싣지 마라.** 기획서만 담은 PR을 9~14단계 절차(문서 게이트)로 병합한 뒤 8단계로 간다.

```bash
git checkout -b docs/<이슈번호>-spec
git add <기획서 경로>
# 9 커밋 → 10 Draft PR → 문서 게이트 → 13 Ready → 14 병합
```

- 제목은 규약의 커밋·PR 제목 형식(없으면 `docs(spec): SPEC-NNNN <제목>`), 본문에 `Refs #N` (**`Closes` 아님** — 이슈는 구현이 끝나야 닫힌다)
- 문서 라벨, Assignee는 현재 인증 사용자
- 리뷰(11·12단계)는 규약이 기획서 PR에 요구할 때만 한다
- 병합 후 8단계 작업 브랜치를 **갱신된 base에서** 새로 딴다

구현 중 기획과 달라진 점은 **구현 PR에서 기획서를 고친다.** 그 diff가 "무엇이 달라졌는가"의 기록이 된다.

## 7단계: 디자인 작성·검증 (조건부)

매트릭스가 지정한 경우에만 (보통 UI 영역 + 기능 유형).

- 저장소에 디자인 스킬이 있으면 사용한다. 차트가 있으면 `dataviz`도 로드
- **소스를 저장소의 디자인 캔버스 폴더에 직접 만든다.** 작업 디렉터리나 스크래치패드에 두지 마라 — 세션이 끝나면 사라지고 다음 작업에서 갱신할 대상이 없어진다
- **기존 캔버스가 있으면 갱신한다.** 새 캔버스를 남발하지 않는다
- 소스에서 재생성되는 발행 산출물은 커밋하지 않는다
- 발행했으면 **URL을 규약이 정한 위치(UI 흐름 문서의 표 등)에 적는다**
- 디자인 시스템 문서의 토큰만 사용
- 규약의 디자인 체크리스트로 검증

## 8단계: 개발·게이트 (조건부)

**직접 구현하고 게이트가 통과할 때까지 고친다.** 종료 조건은 하나 — 게이트 통과, 경고 0.

- 범위는 이슈·기획서(`--no-issue`면 작업 설명)에서 잡는다. 기획 문서 관례가 있는데 없으면 경고한다.
- **반복 개발 모드(`ralph`)를 쓰지 마라.** 키워드 오발동으로 무관한 작업에 모드가 따라붙고, 훅 카운터가 지정 상한을 반영하지 않는다.
- 게이트는 0단계에서 정한 것. 게이트가 없는 영역은 경고 후 통과하되 PR 본문에 명시한다.
- 게이트가 20회를 고쳐도 통과하지 않으면 **거기서 멈추고 원인을 보고한다.** 테스트를 지우거나 약화시켜 통과시키지 않는다.
- 테스트를 새로 추가했다면 **실행 로그에 그 이름이 찍히는지 확인**한다. 통과 개수만 보면 수집되지 않아 조용히 건너뛴 테스트를 놓친다.

### 위임에 대해

병렬화 이득이 확실한 큰 작업이 아니면 직접 구현하는 편이 빠르다.
위임하는 경우에도 **산출물을 직접 읽어 검증**한다. 에이전트의 완료 보고를 근거로 삼지 마라. 정체된 에이전트는 기다리지 말고 중단시키고 직접 처리한다.

> 이 문서와 대화에서 그 모드를 **언급**할 때는 백틱으로 감싼다 — `` `ralph` ``. 평문은 `keyword-detector.mjs`에 걸려 모드를 켠다.

## 9단계: /commit

`~/.claude/commands/commit.md`의 절차를 따른다. 재구현하지 마라.

- **관심사·계층별로 커밋을 나눈다.** 도메인/데이터/화면/테스트/문서를 한 덩어리로 묶지 않는다.
- **순수 파일 이동은 독립 커밋**으로 둔다. `git mv`만 하고 내용을 고치지 않는다.
- 여러 에이전트가 동시에 파일을 만드는 중이면 **경로를 명시해 선택적으로 스테이징**한다(`git add -A` 금지).
- 저장소의 기존 커밋 컨벤션(규약 우선)을 따른다.
- push는 10단계에서 한다.

## 10단계: Draft PR

`~/.claude/commands/create-pr.md`의 절차를 따르되, **PR은 항상 Draft로 생성한다**(`draft: true`, `--open` 금지). Ready 전환은 13단계의 일이다(원칙 A).

본문에 다음을 반드시 포함한다.

- `Closes #N` (기획서 PR이면 `Refs #N`), `--no-issue`면 생략
- 기획서 링크(있으면)
- **구현 중 기획과 달라진 점**과 그 근거
- **구현 중 발견한 결함**과 조치
- 게이트 결과(테스트 건수·린트), 게이트가 없었다면 그 사실
- 자동으로 채울 수 없는 것(스크린샷·실기기 검증)은 **미수행이라고 명시**한다

라벨은 이슈의 type·area 라벨을 따른다. Assignee는 현재 인증 사용자.

**PR 단위를 지킨다** (규약의 PR 단위 규칙이 있으면 그것이 우선):

- 이슈 1개 = 기획서 PR + 구현 PR **2개**. 셋 이상이 필요하면 이슈를 잘못 잡은 것이니 **중단하고 이슈 분할을 제안한다**
- 작업 중 발견한 범위 밖 결함은 **이슈로 등록하고 별도 PR**. 단 **현재 PR의 게이트·검증을 무력화하는 결함은 같은 PR에서 고친다**
  - 판단 기준: "이걸 두면 이 PR이 검증됐다고 말할 수 없는가"
- CI에 변경 크기 경고가 있으면(예: 추가 400줄) **쪼갤 수 없는 이유를 PR 본문에 적는다**

## 11단계: /pr-review

`~/.claude/commands/pr-review.md`의 절차를 따른다. 대상은 10단계에서 만든 PR 번호.

- 이 파이프라인에서는 **작성자와 리뷰어가 동일**하다. 리뷰 결과와 PR 코멘트에 그 사실을 명시한다. 구조적 사각이 남는다는 점을 숨기지 마라.
- 변경 500줄 초과면 외부 리뷰어를 권고하는 문장을 넣는다.
- 위임한 리뷰 에이전트가 **빈 응답으로 끝나면 그 결과를 리뷰로 취급하지 마라.** 직접 검토하고, 위임이 실패했다는 사실을 보고한다.
- Draft PR이므로 submit은 `COMMENT`로 제한된다.

**CRITICAL이 1건 이상이면** 12단계에서 반드시 반영한다. 반영 없이 13단계로 넘어가지 마라.

## 12단계: /apply-review

`~/.claude/commands/apply-review.md`의 절차를 따른다.

- CRITICAL·WARNING은 반영한다. SUGGESTION은 판단하되 **미반영 사유를 남긴다**.
- 반영 후 **게이트를 다시 통과**해야 한다(8단계와 동일한 검증 명령).
- 반영분을 커밋하고 push한다. **이 시점까지 PR은 Draft다.**
- 반영 내역을 PR 코멘트로 남긴다. 무엇을 왜 안 고쳤는지도 함께.

리뷰에서 지적한 내용이 **잘못된 것으로 드러나면** 고치지 말고 정정을 공개한다. 자기 리뷰의 오진을 그대로 코드에 반영하면 더 나빠진다.

## 13단계: Ready 전환 + CI

```
mcp__github__update_pull_request(draft: false)    # 또는 gh pr ready <N>
```

**docs-only이고 CI가 그 경로를 건너뛰면** `list_workflow_runs(branch)`로 실행 0건을 확인하고 14단계로 간다.

그 밖에는 CI를 기다린다.

- `list_workflow_runs(branch, perPage: 1)`로 run id를 확보한다(응답이 크므로 1회만).
- 이후에는 `list_workflow_jobs(run_id)`로 확인한다(응답이 작다).
- **백그라운드 대기 후 조회**한다. 짧은 간격 폴링은 비싸다. 첫 확인은 그 저장소의 과거 실행 시간에 맞춰(모르면 10분), 이후 2분 간격.
- `conclusion: cancelled`면 다른 실행이 concurrency로 취소한 것이다. 같은 브랜치의 더 최신 실행이 있으면 그것을 보고, 없으면 `gh run rerun <run-id>`로 다시 돌린 뒤 기다린다. 취소된 실행의 체크(`fail`)가 PR 체크 목록에 남을 수 있으니 판정은 **최신 실행의 job 결론**으로 한다.
- 그 밖에 `conclusion: success`가 아니면 **중단**하고 실패한 스텝과 로그를 보고한다.
- **push와 Ready 전환을 같은 명령 줄로 잇지 않는다.** 같은 초에 겹치면 Ready 실행이 push 전 head로 돌고 새 커밋은 검사받지 못한다. 성공한 실행의 `head_sha`가 PR head와 다르면 `gh pr ready --undo <N> && gh pr ready <N>`으로 현재 head에 다시 돌린다.

## 14단계: 병합

`--merge`로 병합 직전 확인 여부를 정한다. 규약에 병합 정책이 있으면 그것이 우선한다.

| 값 | 동작 |
|----|------|
| `critical` (기본) | CRITICAL이 0건이거나 모두 반영됐고, 미반영 WARNING이 없고, CI가 통과했으면 확인 없이 병합. 하나라도 걸리면 확인한다 |
| `confirm` | 항상 병합 직전에 확인한다(AskUserQuestion) |
| `auto` | 정지 조건에 걸리지 않으면 확인 없이 병합 |

확인할 때는 PR 번호·제목, CI 결과, 커밋 수, 변경 규모, 미반영 리뷰 지적, 미수행 검증(실기기 등)을 함께 제시한다.

- 병합 방식은 저장소 관례를 따른다(`git log --merges`로 기존 병합 커밋 형태를 확인).
- **merge conflict가 있으면 병합하지 말고 중단**한다.
- 병합 후: base 동기화 → 병합된 브랜치 원격·로컬 삭제(`--no-cleanup`이면 생략).
- 이슈에서 "진행 중" 라벨을 제거한다 (`Closes #N`으로 자동 종료되지 않는 경우).

### 병합 후 (`--post`)

- 진행 문서(작업 계획·로드맵 등)의 체크박스·상태를 실제와 맞춘다.
- 다른 병합 완료 브랜치가 남아 있으면 정리한다.
- **자동화할 수 없는 검증을 사람에게 넘긴다** — 실기기 확인 항목을 체크리스트로 출력한다. 특히 영속·재시작·오프라인처럼 단위 테스트가 덮지 못하는 것.

## 안전 규칙

- **force push · base 브랜치 직접 커밋 · 다른 PR 수정/클로즈를 하지 않는다.**
- 게이트 실패를 우회하려고 테스트를 지우거나 약화시키지 않는다.
- 규약 문서에 없는 라벨·경로·게이트를 지어내지 않는다. 없으면 경고하고 생략하거나 멈춘다.
- 중단할 때는 **어느 단계에서 왜 멈췄는지**와 `--from=N` 재개 방법을 함께 알린다.
- 검증하지 않은 것을 검증했다고 보고하지 않는다. 스크린샷·실기기처럼 못 한 것은 못 했다고 적는다.
- 자가 검증에는 작성자=리뷰어 사각이 있다. PR과 리뷰 코멘트에 명시한다.
